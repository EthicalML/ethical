## [The Databricks Enterprise AI Index](https://developers.databricks.com/ai-index)

How much are enterprises actually using open-weight models nowadays? Databricks published an AI Index built from anonymised Unity Gateway traffic across thousands of enterprises, and it's clear there's an accelerating trend:

Databricks reports open-weight models going from 7.3% to 30.9% of tokens in about four months, with GLM and DeepSeek making up close to 90% of that open-weight traffic. On the proprietary side Anthropic still leads at 61.5% of tokens, but OpenAI more than doubled from 16.4% to 37.0%.

It also seems that multi-provider is the norm now, with 71.1% of companies using two or more providers, against 36.0% in July, and almost half use three or more.

DBX also runs an internal coding benchmark built from their own engineering traces, where Claude Fable 5.1 tops quality at 96.0% for $7.47 per task while GPT 6 Luna gets 89.1% for $0.05 per task (about 150x cheaper).

It is worth keeping in mind this is one vendor's gateway priced at list price, but for production ML teams it is a great data point on where enterprise traffic is heading.

## [Netflix on the AI Discover Harness](https://netflixtechblog.com/engineering-ai-discover-e244944cdc38)

Netflix just published learnings behind their "AI Discover" infrastructure:

The core is what they call an "intelligence layer", which is the agent harness that decides per request how to combine LLMs with their existing recommender systems. They wrap search + ranking + catalog metadata as versioned "capabilities", and each plan is a graph of approved steps over these.

An interesting design decision they shared is that they went with plan-and-execute instead of a ReAct loop. Namely "an LLM can propose the path, but code decides whether it runs". Every plan is validated before it runs (each input has a producer, no loops, exactly one page at the end), and if the planner is slow or fails a check they fall back to a tested plan.

They also enforce the safety rules in code, so maturity ratings and "don't show" preferences are applied by the executor, and the planner only sees placeholders for those parameters, which also helps against prompt injection. As TVs are slow and LLMs are slower, the page is generated async with a "thinking" state on screen while the executor runs in the background.

There are no numbers on latency or engagement yet, which they list as open questions. Still, this is one of the most detailed write-ups we have seen of an agent harness inside a consumer product, so it is definitely worth checking out!

## [Claude Code on Agent Verification](https://claude.dev/blog/how-the-claude-code-team-thinks-about-verification/)

Anthropic published a guide on how they handle software verification - this is one of the most important components in agentic software lifecycle nowadays.

Now that around 90% of their code is written and reviewed by Claude, their argument is that without verification loops one person can supervise one or two agents, while with them it can be dozens running in parallel. They prioritise end-to-end tests first, then property tests (round-trips, invariants, idempotency), then differential tests comparing old and new code during migrations.

There are a bunch of practical patterns in there, like a verify skill next to the code that boots and drives the app before every commit, escalating to a human after 3 failed fix rounds, and a 39-item reliability checklist where only the items triggered by the diff apply. Their code review agent also reads its REVIEW.md from the base branch and never from the PR, so a change can't rewrite its own reviewer!

They also claim up to 10 points of task success from a separate rubric grader; that figure comes from a single internal task type though.

For production ML practitioners the takeaway is that the human role is moving from reading every diff to defining what done looks like and reviewing the evidence.

## [OpenAI's Performance Factory](https://openai.com/index/how-openai-performance-factory-keeps-chatgpt-fast)

OpenAI published how they do software factories internally! They shared their "Performance Factory" which is basically a company-wide agentic loop that extracts insights from their repos, metrics, traces and CPU profiles to investigate and fix regressions in the services behind ChatGPT.

They define each workflow as states in config with a Markdown prompt per state, and a dispatch loop starts a Codex turn whenever a task is ready. A separate Codex session then tries to disprove each diagnosis and each fix, which already caught a root cause that didn't explain the ongoing failures.

In just over 3 months they tracked 1,700+ investigations and root-caused 600+ of them. When engineers reviewed 100 of those root causes, 70% were accurate and 30% needed refinement.

It is interesting to see that engineers reviewing and merging the fixes are now the bottleneck, so they rank tasks by estimated impact to protect engineer attention.

## [HuggingFace on Harness Adapters](https://huggingface.co/blog/harness-adapters-at-scale)

HuggingFace released a framework to optimize models into your own harness;

These are namely LoRA adapters trained with RL inside a specific agent harness so an open model performs better in the harness you actually use.

They trained Qwen3.8-27B adapters for Pi, OpenCode and Hermes Agent, and on a hard 51-task SWE-bench Pro subset the Pi adapter went from 39.2% to 64.7% with 53-70% fewer tool calls. They also merged the three into one super-adapter, which lifts mean pass@1 from 39.5% to 49.0% across all of them.

The authors are quite upfront about the limits, as the merge weight was tuned on Terminal-Bench 2.1 and the Hermes adapter does worse than the base model on an out-of-distribution benchmark.

Following last week's harness leaderboard, it seems the harness is becoming something we tune the model for, and it is great to see the adapters, environments and trajectories all released openly.

## Open Source [MLOps Tools](/open-source/production-ml-list/)

Check out the fast-growing ecosystem of production ML tools & frameworks at [the github repository](/open-source/production-ml-list/) which has reached over 20,000 ⭐ github stars. We are currently looking for more libraries to add - if you know of any that are not listed, please let us know or feel free to add a PR. Here's a few featured open source libraries that we maintain:

- [SARC](https://github.com/besanson/sarc-governance/tree/main) - Provides wrappers for popular agentic frameworks to enable guardrails and constraints that are enforced through the flow.
- [KAOS](https://github.com/axsaucedo/kaos) - K8s Agent Orchestration Service for managing the KAOS in large-scale distributed agentic systems.
- [Kompute](https://github.com/KomputeProject/kompute) - Blazing fast, lightweight and mobile phone-enabled GPU compute framework optimized for advanced data processing usecases.
- [Production ML Tools](/open-source/production-ml-list/) - A curated list of tools to deploy, monitor and optimize machine learning systems at scale.
- [AI Policy List](https://github.com/EthicalML/awesome-artificial-intelligence-regulation) - A mature list that maps the ecosystem of artificial intelligence guidelines, principles, codes of ethics, standards, regulation and beyond.
- [Agentic Systems Tools](https://github.com/EthicalML/awesome-production-genai/) - A new list that aims to map the emerging ecosystem of agentic systems with tools and frameworks for scaling this domain
